# feature-match-check.ts

## Purpose

The page module of `feature-match-check.html`: the guided steps (photo A, photo B, run, save), the camera, the options, the results table, the result pictures and the copyable log. All measuring lives in `bench-run.ts`. It is a view on the page store (`feature-match-store.ts`, state in `feature-match-slice.ts`): taps and option changes dispatch actions, `render` draws the state on every change, and the flat target mode (`flat-capture.ts`) is a second view on the same store.

## Public API

- `startFeatureMatchCheck(root = document)`: wires the page. Throws `feature-match-check: missing <selector>` if the HTML lacks an element it needs.

## Invariants and assumptions

- This file only touches the DOM and browser APIs (`getUserMedia`, `performance`, `navigator.gpu`, `navigator.userAgentData`, the clipboard, canvas encoding); the step logic is `bench-steps.ts`, the drawing `bench-draw.ts`, the files `bench-export.ts`.
- **One action at a time.** A single `busy` state (`idle`, `running`, `saving`) drives every button: during a run or a save, Take photo A/B, Run again, Save and the synthetic run are disabled, so a capture cannot change the pair under a run or under an encode (which would offer old files as new ones). `refresh()` sets every disabled state, label and step mark from the state, so they cannot drift apart.
- **Steps.** Step marks come from `stepStates`: the first step whose work is missing is "current" (with `aria-current="step"`), earlier ones "done". Photo A starts a new pair (it clears B, the run and the offered files); photo B starts the run on the pair by itself. "Run again" re-runs the same pair. The synthetic run (under Options) replaces what Results shows, so it also withdraws the camera run: its results and offered files are dropped, the run step is current again and reads "replaced by the synthetic run: tap Run again", and Save stays off until the camera pair runs again. With no camera run it moves no step.
- **Camera.** Rear camera (`facingMode: environment`), frames kept at most 1280 px on the long side. A capture tap with the camera off only starts it ("camera on: aim, then tap Take photo X"), so the photo is aimed rather than the first frame. The camera stops when any run starts and on `pagehide`. One start is in flight at a time; it is forgotten once it settles, also when it failed before awaiting anything (no camera API at all), so the next tap tries again and logs again. Every stop raises a generation counter; a start still waiting for its stream when a stop happens stops that stream and reports "camera stopped: tap again", so a run never measures beside a live camera. A refused camera shows "camera unavailable (see log)" and an `ERROR camera:` line.
- **Results.** As each method and size finishes, a figure is appended under Results: both frames side by side at one scale (canvas at most 640 device pixels wide), keypoints as dots, at most 200 match lines spread evenly over all matches, and a caption with the counts of the round drawn ("last round: keypoints A n, B n | matches n") and the median times; the table and report show the lower median over all rounds, which may differ for a method whose output varies. A failed size or method gets a red caption card instead. The table and report are written when the run ends.
- **Options check.** A ticked method left with no backend (or XFeat with no model file) is refused before the run with an `ERROR options:` line naming it (`selectionGaps`), rather than dropped without a word.
- **Pair names.** Step 1 holds a Pair selector (the `PAIRS` list) and a Spot field (1-3). Photo A raises the running number and fixes the pair from both (`pairTag`), shown as "now: pair N, <key> <label>, spot S" and logged; changing the selector afterwards does not relabel the pair in progress. A photo B taken again after any of the pair's files was downloaded (the zip or a single file) is a new take: it raises the running number (shown "now: pair N, ..." again), so its files never reuse the saved names. Save offers every download under `pairFileNames` of that pair (the zip's entries keep the fixed `FRAME_FILES` names) and writes the pair and the page load's `sessionToken` into the frames JSON.
- **Progress across reloads.** The running number, the selected pair and the spot are stored in `localStorage` (`progressText`) at every photo A, every move after Download all and every change of the selector or spot, and read back at start (`parseProgress`), so a reload or a discarded tab continues the numbering. Both reads and writes are in try/catch: with storage blocked every load starts at pair 1, and the random session token (4 bytes, no time, no place) tells such runs apart. The first download of a pair's files (Download all or any single file) moves the selector and spot on with `nextPair` (from the pair in progress, not from the selector's current value) and logs "next pair: ..."; a second tap saves again and moves nothing.
- **Guidance.** Step 1 opens with a "Before you start" box listing `BEFORE_YOU_START`; it is open on the first visit and closed on later ones (a `localStorage` flag, read and written in a try/catch: with storage blocked it is open every time). Under the Pair selector a card shows the selected pair's `PAIR_GUIDE` entry: the purpose, the steps as a numbered list, "Avoid: ..." and, for the light pairs, the spot note. It follows every change of the selector, also the move after Download all. The selector lists `PAIRS` and then "none: manual run with the Options".
- **Photo test settings.** A camera run whose pair (fixed at photo A) is a protocol pair runs with `runSettings`: 1 run, no warm-up, WebGPU only (WASM where `navigator.gpu` is missing or `requestAdapter()` gives no adapter or throws, asked once per page) and the fp16 XFeat file, whatever the Options say; the Options' methods and sizes still apply. The Options say so in one line ("Photo tests set these themselves ...", the WASM fallback included), and so does the hint of step 3. The pair `none` and the synthetic run use the Options. The run logs the `runs:` line of what was used, and the report states runs and warm-up.
- **Light check.** At photo B of a light pair the two frames' grey means go through `lightCheck` and the result is logged (`light check: ...`). A failed check shows a red `role="alert"` warning at the top of Results. For a dimmed pair: "Photo B is not darker than photo A - the light has to change BETWEEN the two photos ...", which also offers to dim further (the camera brightens a dim picture by itself). For an almost black photo A of a dimmed pair: "Photo A is almost black ...". For a black photo B of a dimmed pair: "Photo B is black ...". For the control pair: "... the light changed during the control pair ...". The result goes into the frames JSON as `lightCheck`. After Download all, a failed pair keeps the selector on itself (logged "pair kept: take <key> again") so the tester repeats it. A new photo A or B clears the check and hides the warning.
- **Copy log** carries a note that the photo tests do not need it (the zip holds the log); it is for pasting a quick timing run into a chat.
- **Save after a run.** Save is enabled once the camera run has ended, whatever it came to. After a run with results it reads "ready: tap to prepare the files"; after a run that measured nothing (refused options, nothing ticked, a run that threw) it reads "nothing measured: tap to save the photos anyway", and the matches JSON then lists no methods.
- **Save.** Shows "preparing...", then encodes both frames as PNG through a canvas, checks them with `assertPlainPng`, packs them with the log and the report (`allFilesZip`, the log as it reads when Save is tapped) and offers five links, "Download all (zip)" first, then both PNGs, `feature-match-frames.json` and `feature-match-matches.json`, with "ready: tap Download all (zip), or each file". On a failure every offered link is withdrawn (blob URLs revoked), the state reads "failed (see log)", an `ERROR save:` line is logged and Save is enabled again.
- Device facts that cannot be read fall back to `UNKNOWN_DEVICE` with a log line; they never stop a run.
- Every failure (camera refused, nothing ticked, a method that fails, a page error, an unhandled rejection) becomes an `ERROR ...` log line and goes into the report; buttons come back in a `finally`.
- Resource timing's buffer is raised to 1000 entries so a long run keeps the download sizes.
- **State in the store.** The pair flow (numbering, retake rule, the advance after a download, the light check), one action at a time, the run and save status, the status lines, table, report, log and errors, and the options all live in the slice; its reducers hold the rules. The options are mirrored from the controls on every `input`/`change` and read from the state at run time. Log lines are stamped with the page time here and stored finished.
- **Outside the store**, as browser resources: the camera stream, its start in flight and its generation counter, the result pictures (canvases drawn during a run), and, in the store's side tables keyed by the ids the state holds, the photo frames, the run's results and the offered Blob URLs. A side table entry is put in place in the same step as the action that names it, since the store drops every entry the state does not name.
- **Drawn only when moved:** the selector and the spot field are written only when the state changed them (a field being typed in is never overwritten), and the links, table, report and log only when their part of the state changed.

## Example

```html
<script type="module">
  import { startFeatureMatchCheck } from "./src/checks/feature-match/feature-match-check.ts";
  startFeatureMatchCheck(document);
</script>
```

- **Speed test.** A `Speed test` section times the XFeat fp16 reference, DINOv2-S/14 (int8, q4f16) and SIFT + LightGlue, per ticked backend, on one pair at the chosen long edge (480/640/960) and SIFT cap (512/1024), N runs (`parseTimingRuns`, default 10). It uses the camera pair when both photos exist, else the synthetic pair, stops the camera and withdraws the camera run like the synthetic run. `runTimingByGroup` (`bench-timing.ts`) runs each backend group alone, one after another, and interleaves its arms in a balanced order per round. While it runs, `guardRun` (`run-guard.ts`) holds the screen wake lock (taken again when the page comes back) and records a hidden page: the report then carries `ERROR page was hidden during runs`; the report (`formatTimingReport`, download size and time, start-up, first run, steady median and p90, the backend, the ratio to the group's reference) goes into the Report box and so into Copy log. The button reads "Timing..." and every button is off while it runs (`busy` = `running`); the state reads "done: N arms" with the count of arms that failed, or "not run: nothing ticked". An arm that fails to load is an `ERROR load:` line in its section, never a stopped test. `#m-siftlg` adds SIFT + LightGlue to the normal benchmark (unticked by default: 46 MB).
- **Flat target mode.** The selector's `flat` entry (`FLAT_MODE`) is a mode, not a pair: choosing it stops the page camera and opens `flat-capture.ts` full screen; Exit (or another selector value) closes it and puts the last pair back. The choice is kept across reloads like a pair, and the guidance card is not shown for it. The canvas helpers live in `bench-dom.ts`.

## Tests

`playwright-tests/feature-match-check.spec.js`: stubbed SIFT on the synthetic pair (table, report, picture, phone width), a 404 for `sift.js`, the guided camera flow with a faked camera (auto run, buttons disabled while the run is held, grey values near 127.5, steps, the zip and the four saved files checked, the pair picked before A fixed while the selector is changed between A and B, every name carrying it, the frames JSON's pair fields and the selector moved on after Download all), a failed save (in-progress state, buttons disabled while encoding, links withdrawn, error logged, button back), a refused camera, a camera start overtaken by a run, a run that measured nothing (options gap and a run that throws, with the save label for both), a camera start that fails at once and is retried, a synthetic run that withdraws the camera run's files, the guidance card following the selector (purpose, step count, avoid line, spot note) with "Before you start" open on the first visit and closed after a reload, the Options and Copy log notes, and a photo test pair run with the Options untouched (log `runs:` line, report settings line and method headers: one run, no warm-up, one backend, one XFeat file), with a faked WebGPU adapter, with `navigator.gpu` but no adapter, and without `navigator.gpu` (WASM fallback named for both). WebGPU counts only when `requestAdapter()` gives an adapter; it is asked once per page and a throw counts as none. There is also a light check: the fake camera dims (`window.__dim`) between A and B in the guided flow (check "ok"); a 1b pair with no dimming shows the warning, writes "not-darker" and keeps the selector; retaking only photo B, dimmed, gets pair 2 and a new file name, checks "ok" and moves on; and a control pair that is dimmed warns "changed". Downloading only the single frame B file marks the pair saved too: a retaken photo B gets pair 2 and the 02 file name. A reload continues the numbering ("now: pair 2, ..." and the 02 file name, a new session token), and with storage blocked two loads both start at pair 1 with different session tokens. The guided flow also runs size 480 on the 320x240 camera, so a saved keypoint is checked through a mapping that is not the identity. The speed test reports an arm that cannot load (network refused) and refuses to run with nothing ticked. A flat target surface is captured end to end (`flat-capture.ts.md` has the list). The browser-only code has no unit test.
